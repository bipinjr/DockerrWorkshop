Why this matters

From tool to deployable service

This project walks through taking a LangChain tool with a Pydantic schema, wrapping it in a FastAPI server, containerizing it, and deploying it — the full path from notebook code to a live endpoint.

1

Define the tool

@tool with a docstring and a Pydantic input schema — typed, validated, self-documenting.

2

Wrapping it

FastAPI exposes the tool as HTTP endpoints. GET / for health, POST /weather to run it.

3

Containerize

Dockerfile builds a slim image. .dockerignore keeps secrets and caches out. One docker run starts it.

4

Validate inputs

Empty city → ValueError. Missing API key → ValueError. The errors are clear, not cryptic stack traces.

5

Secrets out of code

WEATHER_API_KEY lives in .env locally and in the cloud platform's env dashboard — never committed.

6

Deploy anywhere

Push to GitHub. Connect Render or Railway. Set the key in their dashboard. One live URL, callable from anywhere.

Cloud deploy

Get it live in minutes

The repo is ready — connect it to a platform, set one environment variable, and you have a public URL.

R

Render

New Web Service → connect the GitHub repo → let it detect the Dockerfile → add WEATHER_API_KEY in Environment Variables → deploy.

# Set this in the Render dashboard WEATHER_API_KEY=your-actual-key
Y

Railway

New Project → Deploy from GitHub → Railway picks up the Dockerfile → add WEATHER_API_KEY under Variables → deploy.

# Same variable, different dashboard WEATHER_API_KEY=your-actual-key

Remember: the .env file is excluded from Git (.gitignore) and from the Docker image (.dockerignore). The key only enters the picture via the platform's environment variable dashboard — never in code, never in the repo.
